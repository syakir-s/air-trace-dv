accelerometer_spi_master testbench - how it works

1. This testbench verify the accelerometer_spi_master module. In this testbench the master steps through ~93 states to drive the SPI write-configuration then read sequence (write config → read). Allowing Nexys A7 100T communicate correctly with accelerometer ADXL 362. All the states is run from the dut to verify correct sequence allowing precise communication. Fake data injected and compared with acl_data (data captured b the master).
2. Reactive slave BFM is use to simulate slave drive and compare if the system really run with correct instruction (slave drive negedge, master sample posedge). Basic protocol is verify (cs run low during slave drive). Reactive slave BFM allow us to debug the exact timeframe MISO drive to produce accurate acl_data. The BFM responds to the visible SPI signals (sclk, cs) like a real ADXL362 would, not to the master's internal state, so it models the interface contract, not the DUT's guts.
3. Distinct per-axis bytes is used to allow me to verify if theres any bug such as axis swap since the per-axis data is explicit for each.
4. The captured acl_data came out as 48b0 instead of the expected 1d03. The wrong value was my injected data shifted by one bit, not random (garbage). Which pointed to a timing misalignment, not a data error. 
Cause: I initially set the drive threshold to 16 (matching the 16 command/address bits), but that made the slave present the first data bit one falling-edge too late. After the master had already taken its first sample, so the master captured stale MISO and every bit shifted by one. Because the slave drives on the falling edge and the master samples on the next rising edge, the first data bit must be driven at count 15, one edge earlier, to be stable when sampled. Fixing the threshold to 15 aligned it → acl_data = 1d03. Confirmed on the waveform: MISO shows the MSB of x_lsb starting at count 15.
